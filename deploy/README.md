# Развёртывание СКЗ с PostgreSQL

Комплект содержит отдельную серверную версию интерфейса, Flask API, PostgreSQL, фоновую обработку уведомлений и архивации, HTTPS-прокси и ежедневные резервные копии. Демонстрационные учётные записи и заявки не загружаются в рабочую БД. Старый сайт на chatgpt.site остаётся демонстрацией.

## Подготовка сервера

Linux-сервер с Docker Engine и Docker Compose v2. Стартовая конфигурация для проверки: 4 CPU, 8 ГБ RAM, SSD; фактические ресурсы уточняются нагрузочным тестом на целевом сервере. Нужны домен с DNS-записью на сервер и открытые TCP 80/443 для HTTPS. PostgreSQL наружу не публикуется.

1. Скопируйте каталог проекта на сервер, перейдите в него.
2. Скопируйте `deploy/.env.example` в `deploy/.env`, ограничьте права: `chmod 600 deploy/.env`.
3. Создайте два независимых секрета: `openssl rand -hex 32` — отдельно для `POSTGRES_PASSWORD` и `SESSION_SECRET`. Укажите временный пароль администратора в `ADMIN_INITIAL_PASSWORD`. Значения-заглушки оставлять нельзя. Для пароля БД используйте только hex, чтобы URL подключения не требовал экранирования.
4. Для публикации задайте `APP_DOMAIN=ваш.домен` и `APP_ORIGIN=https://ваш.домен`. Временный пароль с символом `$` в `.env` заключайте в одинарные кавычки.
5. Проверьте конфигурацию без вывода секретов: `docker compose --env-file deploy/.env config --quiet`.
6. Запустите: `docker compose --env-file deploy/.env --profile public up -d --build`.
7. Проверьте `docker compose --env-file deploy/.env ps` и откройте HTTPS-адрес. Войдите как `admin` с временным паролем. Смена пароля обязательна; прежний пароль после смены не действует.

Для локальной приёмки без публичного домена оставьте `APP_ORIGIN=http://localhost:8080` и запускайте без `--profile public`. Приложение доступно только на loopback сервера; для доступа со своего компьютера используйте SSH-туннель `ssh -L 8080:127.0.0.1:8080 user@server` и откройте `http://localhost:8080`.

Миграции и создание администратора выполняет одноразовый контейнер `migrate`. Повторный запуск сохраняет БД и не сбрасывает пароль. Приложение и worker стартуют только после успешной миграции. `docker compose down` сохраняет данные; не используйте `down -v` для рабочей системы.

## Приёмка перед допуском пользователей

- Проверить обязательную смену пароля, невозможность входа со старым паролем, блокировку пользователя и завершение его сессии.
- Создать пользователей всех ролей; проверить ограничения видимости и назначения, включая тёзок и изменение ФИО.
- Импортировать тестовый файл, проверить дубликаты, выполнить оба этапа заявки и выгрузку. Убедиться, что данные сохраняются после перезапуска.
- Проверить два разных времени возврата в один день; уведомление появляется в пределах 30 секунд. Открытие не снимает «Новую заявку»; реальное сохранение изменения снимает.
- Проверить, что незавершённые заявки старше двух месяцев остаются в работе, а завершённые архивируются и недоступны для редактирования.
- Выполнить нагрузочный сценарий для 50 одновременно работающих пользователей, импорт 9999 строк и выгрузку за 45 дней. Локальные проверки кода не подтверждают SLA сервера.

## Резервное копирование и восстановление

Контейнер `backup` создаёт `pg_dump` сразу при старте и затем каждые 24 часа. Срок хранения — 30 дней. Копии находятся в Docker-томе `skz_backups`, содержат БД целиком, включая пользователей, заявки, архив, журнал и шаблоны. Контролируйте `docker compose --env-file deploy/.env logs backup`; сбой завершает контейнер с ошибкой и вызывает его перезапуск.

Копии на том же сервере защищают от ошибки приложения, но не от потери сервера. Настройте перенос копий на отдельное хранилище средствами инфраструктуры.

Проверка восстановления выполняется сначала в отдельной тестовой БД. Экспорт копии на хост:

```sh
docker compose --env-file deploy/.env exec backup ls -l /backups
docker compose --env-file deploy/.env cp backup:/backups/ИМЯ_КОПИИ.dump ./restore-test.dump
docker compose --env-file deploy/.env exec db createdb -U skz skz_restore_test
docker compose --env-file deploy/.env exec -T db pg_restore -U skz -d skz_restore_test --no-owner < restore-test.dump
docker compose --env-file deploy/.env exec db psql -U skz -d skz_restore_test -c 'SELECT count(*) FROM requests;'
```

Для восстановления рабочей БД требуется отдельное окно обслуживания: остановить приложение и worker, сохранить текущую БД, восстановить проверенную копию в новую БД и переключить подключение. Не выполняйте удаление рабочей БД по инструкции для тестового восстановления.

## Обновление

Сделайте свежую резервную копию, доставьте новый комплект, затем повторите `up -d --build`. Перед изменениями схемы добавляется новая нумерованная миграция; первоначальную применённую миграцию менять нельзя. Логи: `docker compose --env-file deploy/.env logs --tail 100 app worker migrate`. Health endpoint `/api/health` проверяет подключение к БД.

## Особенности реализации

Время бизнес-процесса — Москва. Пароли bcrypt, сессии в БД на 12 часов, HTTPOnly/SameSite cookies, Secure при HTTPS, Origin+CSRF проверки, экранирование выводимых данных и CSP. Изменения заявок используют номер ревизии: конфликт сохранения требует повторного открытия карточки. Файлы выгрузки создаются динамически, шаблоны сохраняются в БД.

Для расчётов сервер обязан прочитать дату регистрации. Нераспознаваемая дата останавливает импорт с сообщением; остальные текстовые поля не проверяются на тип. Это необходимое уточнение к исходному требованию «типы не проверять». Изменение календаря пересчитывает неархивные заявки; на большом объёме выполняйте его вне пикового времени.

До фактического запуска на сервере не подтверждены: миграция в настоящую PostgreSQL, HTTPS/DNS, восстановление копии и производительность при 50 параллельных пользователях. Эти проверки перечислены здесь как обязательная приёмка, а не как пройденные тесты.
